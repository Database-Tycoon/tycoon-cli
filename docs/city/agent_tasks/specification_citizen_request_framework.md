# Technical Specification: The Citizen-Request & Logistics Framework (CRLF)

## 1. Conceptual Overview
The CRLF transforms the simulation from a static state-machine into a **Reactive Economic Ecosystem**. It models the tension between **Demand** (Citizens), **Supply** (Engineers/Blueprints), and **Flow** (Logistics/Shipments).

The core loop is:
1.  **Demand:** Citizens generate `DataRequests` based on unmet needs.
2.  **Supply:** Engineers resolve requests by implementing `Blueprints` (Markdown tasks).
3.  **Flow:** Once infrastructure is built, `Shipments` move data from external sources into the city.

---

## 2. The Three Pillars of the Framework

### A. The Demand Pillar (Citizens & Requests)
Represents the "Why" of data engineering.

*   **Citizen:** An entity in the simulation with `patience` and `needs`.
    *   **Needs:** A set of required data attributes (e.g., `traffic_density`, `weather_temp`).
    *   **Patience:** A decaying value. If patience reaches zero before a request is fulfilled, the citizen's "Happiness" drops significantly (representing loss of trust).
*   **DataRequest:** A formal requirement generated by a Citizen.
    *   **Types:** `DATA_SOURCE` (New road), `SCHEMA_CHANGE` (Widening a road), `QUALITY_FIX` (Repairing a bridge), `PERFORMANCE` (Adding lanes).
    *   **Status:** `PENDING`, `IN_PROGRESS`, `FULFILLED`, `EXPIRED`.

### B. The Supply Pillar (Engineers & Blueprints)
Represents the "How" of data engineering.

*   **Blueprint (Markdown Task):** A structured instruction file located in `docs/agent_tasks/*.md`. It defines the technical requirements to resolve a specific type of `DataRequest`.
*   **Engineer (The Agent):** The actor that consumes Blueprints to transform the simulation's code/configuration, thereby moving a `DataRequest` from `PENDING` to `FULFILLED`.

### C. The Flow Pillar (Logistics & Shipments)
Represents the "What" of data engineering.

*   **Shipment:** A discrete unit of data movement from an external `Source` to the city's `Landing Zone`.
*   **Logistics Hub (The Port):** The entry point for all shipments. It handles:
    *   **Unloading:** Moving data from the shipment into the simulation state.
    *   **Customs (Validation):** A mandatory check where data is validated against the `Contract`. If validation fails, the shipment is "Contraband" and must be discarded or repaired.
*   **Logistics Route:** The pipeline/connection that allows shipments to travel from `Source` $\rightarrow$ `Hub`.

## 3. Data Model (The "Contract")

### Request Schema (`contract/fixtures/request_schema.json`)
```json
{
  "type": "object",
  "properties": {
    "request_id": { "type": "string", "format": "uuid" },
    "citizen_id": { "type": "string" },
    "timestamp": { "type": "string", "format": "date-time" },
    "priority": { "enum": ["LOW", "MEDIUM", "HIGH", "CRITICAL"] },
    "request_type": { 
      "enum": ["DATA_SOURCE", "SCHEMA_CHANGE", "QUALITY_FIX", "PERFORMANCE"] 
    },
    "description": { "type": "string" },
    "status": { "enum": ["PENDING", "IN_PROGRESS", "FULFILLED", "EXPIRED"] },
    "complexity": { "type": "integer", "minimum": 1, "maximum": 10 }
  },
  "required": ["request_id", "citizen_id", "timestamp", "priority", "request_type", "status"]
}
```

### Shipment Schema (`contract/fixtures/shipment_schema.json`)
```json
{
  "type": "object",
  "properties": {
    "shipment_id": { "type": "string", "format": "uuid" },
    "route_id": { "type": "string" },
    "payload_size": { "type": "integer", "description": "Size in MB" },
    "arrival_time": { "type": "string", "format": "date-time" },
    "is_contaminated": { "type": "boolean", "description": "True if validation failed at Customs" }
  },
  "required": ["shipment_id", "route_id", "payload_size", "arrival_time"]
}
```

## 4. Implementation Roadmap

### Phase 1: The Foundation (Core Logic)
*   [ ] Implement `src/tycoon_city/sim/requests.py` (Request management).
*   [ ] Implement `src/tycoon_city/sim/logistics.py` (Shipment and Hub logic).
*   [ ] Implement `src/tycoon_city/sim/citizens.py` (Citizen behavior and patience).

### Phase 2: The Integration (The Loop)
*   [ ] Connect `LogisticsHub` to the simulation tick (Shipments arrive over time).
*   [ ] Implement "Customs" logic in `logistics.py` using existing contract schemas.
*   [ ] Implement the "Request-to-Blueprint" mapping logic.

### Phase 3: The Interface (Observability)
*   [ ] **CLI:** `tycoon-city request list`, `tycoon-city shipment status`.
*   [ ] **Web UI:** A "City Dashboard" showing:
    *   Active Requests (The Backlog).
    *   Current Shipments in transit.
    *   Citizen Happiness (based on request fulfillment).

## Addendum (2026-08-05): how CRLF fits the existing architecture

*Added by the resident agent; Stephen's specification above is authoritative
for the framework itself. This section binds it to the repo's standing laws.*

- **CRLF is the SIMULATED layer** from the Phase-G three-layer design
  (Derived / Presentation / Simulated). Citizens, patience, happiness and
  requests write their own fields only, run on tick + seed, and may never
  mutate derived facts (freshness, test status, load). Guard in the spirit of
  `test_no_pygame`: snapshot derived state, tick 100 times, assert
  byte-identical. Until Stephen flips the default, simulated features ship
  behind a URL flag (the `?guests=1` pattern) and wear a "simulated"
  provenance label in any panel that shows them.
- **The city runs on a REAL catalog** (Database Tycoon, module `tycoon_city`;
  "Pipeline City" is the retired name). Logistics should reuse measured flow
  where it exists — dlt loads and dbt builds are the real shipments; the
  Customs metaphor maps onto contract validation that already exists
  (zod + the schema fixtures). Where CRLF needs synthetic sources (the
  weather module), they live in demo/fixture projects, never in
  `~/clients/dogfood`, and NO TEST may touch dogfood.
- **Request/shipment records carry uuids and timestamps, so they must NOT
  enter `city.json` v1** (byte-stable, golden-tested). They are their own
  documents against their own schemas in `contract/fixtures/`.
- **Blueprint workflow:** own git worktree + branch; suites green
  (`uv run pytest -q`, `npx tsc --noEmit`, Playwright on an unshared port);
  render-and-look for anything visual; dated `../log.md` entry; local
  commits only — never push, never open PRs; report branch + SHAs + what was
  deliberately left out. Wrong-axis discipline: break the code a new test
  names and watch it fail before trusting it.
